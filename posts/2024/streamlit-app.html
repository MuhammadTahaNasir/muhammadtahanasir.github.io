Building My First AI App in 3 Days: Headstarter Fellowship Reflection

July 27, 2024 • 5 min • Muhammad Taha Nasir

This summer, I took a massive leap and joined the New York-based Headstarter AI Software Engineering Fellowship. Navigating the 9-hour time difference from Pakistan meant powering through late-night standups and midnight hackathons, but the experience was unbelievable.

Working alongside talented teammates across global universities, I learned how to move at breakneck execution speeds shipping weekly full-stack AI products. One of my favorite builds from the fellowship was the AI Roadmap Generator, a Streamlit app we designed and shipped in just 72 hours.

Rapid Prototyping & The First Impression

So, I've spent the last month building and shipping a new AI product every single week. And if you're tracking software engineering right now, you know the game has completely changed. We are no longer in an era where spending six months building a basic web wrapper or custom backend before testing a product with users makes sense.

This is where Streamlit completely blew my mind. Coming from a Python-heavy background in Machine Learning, Streamlit allowed us to take a raw open-weights reasoning model Google's newly released Gemma 2 9B and wrap it inside an interactive, functional web application without getting bogged down in complex frontend setup.

The responsiveness of rapid prototyping frameworks is incredible. You focus on the core value proposition, wire up your model APIs and database authentication, and deploy directly to the cloud. But shipping fast means hitting unexpected bugs at 3 AM. How did we take this from idea to live deployment? Let's find out.

Under the Hood in 100 Seconds

Imagine spending two days building a web application, only for user sessions to completely drop on every single page refresh because your authentication SDK call wasn't persisting state properly. Welcome to rapid prototyping.

# Streamlit Interface & State Management Snippet
import streamlit as st
import firebase_admin
from firebase_admin import credentials, auth

st.set_page_config(page_title="AI Roadmap Generator", layout="wide")

st.title("AI Roadmap Generator ")
st.write("Generate a personalized learning path powered by Gemma 2 9B!")

# User Input Entry
user_goal = st.text_input("Enter your target career or learning goal:", placeholder="e.g., Full-Stack AI Engineer in 2024")

if st.button("Generate Roadmap"):
    if user_goal:
        with st.spinner("Analyzing skill dependencies and prompting Gemma 2 9B..."):
            # Model inference call & Firebase session storage
            st.success("Roadmap Generated!")
            st.markdown(f"### Custom Learning Path for: **{user_goal}**")
    else:
        st.warning("Please enter a learning goal first!")

Historically, building an app with user authentication and dynamic AI generation required a full stack: React on the client, Node/Express on the API layer, and a dedicated database server.

The Headstarter Rapid Stack compresses that architecture into three core components:

  1. Frontend (Streamlit): Turns simple Python variables into interactive web components, handling state reloading on user inputs.
  2. Backend Storage (Firebase): Manages secure user authentication, persistent user profiles, and session storage.
  3. Inference (Gemma 2 9B): Google's open-weights model generates structured, step-by-step learning roadmaps tailored to the user's specific skill level.

When we first deployed, Gemma 2 9B had sluggish cold-start response times. We optimized the pipeline by implementing caching mechanisms for common query structures, speeding up roadmap generation significantly. Take the absolute L on slow initial API calls.

The Systems Engineer's Rant

LOOK AT THIS STATE RERENDER! JUST LOOK AT IT!

I am watching developers build Streamlit applications without understanding how Streamlit's execution model works under the hood, and I am physically losing my mind!

# What beginners do in Streamlit that causes infinite execution loops:
import streamlit as st

# EVERY TIME A BUTTON IS CLICKED, THE ENTIRE PYTHON SCRIPT RERUNS FROM TOP TO BOTTOM!
data = heavy_model_load() # RE-LOADING A 9B PARAMETER MODEL ON EVERY SINGLE BUTTON CLICK!!

You guys are out here building Streamlit apps without using @st.cache_resource or @st.cache_data, forcing your server to re-execute expensive computations on every single interaction!

It is NOT BLAZINGLY FAST!

In Streamlit, script reruns happen top-to-bottom on every user interaction. If you don't wrap your model initializations and database connections in caching decorators, you crush your server performance!

# THIS IS HOW YOU WRITE FAST STREAMLIT CODE:
@st.cache_resource
def load_gemma_model():
    return initialize_model_connection() # Loaded ONCE in memory!

Stop reloading your models on every button click and learn how state caching works!

Late-Night Deployment & Teamwork Stress Test

So, writing Streamlit code locally is straightforward. But what happens when you collaborate across time zones with a team member in a high-stakes sprint right before a deadline?

A huge shoutout to my teammate Awwab, who handled our production deployment like an absolute pro, hosting the live app on Streamlit's platform (ai-roadmap-generator.streamlit.app).

(Linus walks past the desk, trips over an ethernet cable, and drops an external battery pack onto the floor)

...Okay, that power bank has an aluminum casing. The LED status light is still green!

When you deploy Streamlit apps to the cloud, missing environment variables (secrets.toml) or misconfigured API keys will instantly crash your live app while local testing works fine.

Debugging Firebase authentication SDK state mismatches across late-night calls taught us that real-world software engineering is 20% writing code and 80% communication, debugging, and environment configuration!
