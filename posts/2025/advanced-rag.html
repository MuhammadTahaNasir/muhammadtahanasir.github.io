Why Basic RAG Failed My AI Study Assistant and How I Fixed It

The Problem with Semantic Search

Let's talk about building retrieval-augmented generation (RAG) systems in the real world. A few months ago, I thought building a personalized AI study assistant for my computer science notes would be a straightforward weekend project. I had hundreds of PDFs, lecture slides, and personal Markdown notes. The standard playbook is easy: chunk the text, generate embeddings using an OpenAI or Hugging Face model, shove those embeddings into a vector database like Pinecone or FAISS, and query them when the user asks a question.

The first few queries worked like magic. If I asked, "What is a neural network?", the system correctly pulled the introductory paragraph from my deep learning textbook. It felt incredibly powerful. But then, I asked a highly specific, complex question: "Compare the performance trade-offs between QuickSort and MergeSort specifically concerning worst-case scenarios, based on my Week 4 Data Structures lecture."

The AI completely broke down. It hallucinated terribly. It pulled a paragraph about sorting from a completely different context, mixed it up with some random runtime complexities from a database course, and gave me an answer that would absolutely fail a midterm exam. I was shocked. How could a system that understands the "meaning" of text fail so spectacularly on a direct comparison?

Why Embeddings Fall Short

To fix the issue, I had to fundamentally understand how semantic search actually works under the hood. Vector embeddings map text to a high-dimensional space based on conceptual similarity. Words that appear in similar contexts in the training data end up close together in this mathematical space.

However, this means that vector databases measure conceptual distance, not relational logic. If I search for the exact variable name "x_train_split_v2", a pure vector search might just return general paragraphs about splitting datasets, completely missing the exact variable I need. Semantic search is terrible at needle-in-a-haystack exact keyword matching. It understands the "vibe" of your query, but ignores the strict constraints.

The Solution: Hybrid Search

The immediate fix was implementing Hybrid Search. If semantic search is great for meaning but terrible for exact keywords, and traditional database search is great for keywords but terrible for meaning, combining them gives you a bulletproof retrieval system.

In industry, this is standard practice. You run the user's query through two parallel pipelines: one semantic (vector search) and one lexical (keyword search). You retrieve the top results from both, merge the lists, and mathematically rerank them to surface the documents that score highly on both metrics.

How BM25 Fills the Gap

For the lexical search component, I used BM25 (Best Matching 25). BM25 is a robust ranking function used by search engines to estimate the relevance of documents to a given search query. It operates on term frequency-inverse document frequency (TF-IDF). Unlike embeddings, BM25 cares exactly about the specific words you typed.

If I ask about "QuickSort", BM25 will hunt down the exact instances of that string, completely ignoring general texts about sorting algorithms. By combining FAISS (for vectors) with BM25, the system suddenly became incredibly sharp and precise.

Ensemble Retriever Code

Here is exactly how I implemented this in Python using LangChain. I created an Ensemble Retriever that assigns specific weights to the vector search and the keyword search.


from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings

# Step 1: Initialize the exact keyword matcher (BM25)
# This will hunt for exact string matches in my study notes
bm25_retriever = BM25Retriever.from_texts(my_uni_notes)
bm25_retriever.k = 3 # Retrieve top 3 exact matches

# Step 2: Initialize the semantic vector matcher (FAISS)
# This handles the conceptual understanding
embeddings = OpenAIEmbeddings()
faiss_vectorstore = FAISS.from_texts(my_uni_notes, embeddings)
faiss_retriever = faiss_vectorstore.as_retriever(search_kwargs={"k": 3})

# Step 3: Combine them using an Ensemble Retriever
# I heavily weight the semantic search, but keep BM25 strong enough to anchor facts
ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, faiss_retriever],
    weights=[0.4, 0.6] 
)

# Execute the hybrid search
retrieved_docs = ensemble_retriever.invoke("QuickSort vs MergeSort worst-case time complexity")

for doc in retrieved_docs:
    print(doc.page_content)

Moving to Graph Databases

Hybrid search fixed 80 percent of my hallucination problems. But what about the remaining 20 percent? The system still struggled to connect the dots between concepts spread across entirely different lectures. For example, if Lecture 1 defined a "Foreign Key" and Lecture 5 explained "Database Normalization", the AI couldn't inherently link them unless they were physically near each other in the text chunks.

This led me down the rabbit hole of Graph RAG. Instead of storing flat text chunks, you use an LLM to extract entities and relationships before saving them to a graph database like Neo4j. You literally map out the knowledge. "Foreign Key" is stored as a node, with a relationship arrow pointing to "Normalization". When queried, the system traverses these relationships, pulling a highly structured web of context. It is incredibly complex to set up, but the results are astonishingly accurate.

Engineering Takeaways

This project was a massive reality check. It taught me that in the world of AI, data structure is absolutely everything. You can pay for the most expensive, highly parameterized language model on the planet, but if your retrieval architecture is garbage, your output will be garbage.

Start with vector search, graduate to hybrid search with BM25, and if you are building enterprise-grade systems where hallucinations are unacceptable, look heavily into Graph RAG. Keep building, keep failing, and keep optimizing.
