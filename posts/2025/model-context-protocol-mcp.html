What is Model Context Protocol (MCP)? Connecting LLMs to Enterprise Data

Introduction & The N×M Integration Problem

Building enterprise AI applications used to mean tackling a painful N×M integration problem. Every AI host application or workflow system required custom connectors for every internal database, CRM, and cloud API. If you wanted Claude, ChatGPT, or an internal agent to query PostgreSQL, GitHub, and Jira, you ended up writing and maintaining bespoke API wrappers for each combination.

Introduced by Anthropic, the Model Context Protocol (MCP) acts as an open standard, often called the "USB-C port for AI", that unifies how LLMs connect to external data sources, tools, and execution environments.

Instead of building fragmented custom connectors, developers write an MCP server once, allowing any compatible LLM host (Claude Desktop, Cursor, AI agents, enterprise pipelines) to safely interact with those data sources.

Architectural Anatomy: Host, Client, and Server

MCP separates concerns by defining clear boundaries between the user application, the LLM orchestration layer, and external data systems:

  • MCP Host: The front-end or environment where the AI user session lives (e.g., IDEs, internal agent frameworks).
  • MCP Client: Embedded within the host, handles connection lifecycle, capability negotiation, and protocol enforcement with MCP servers.
  • MCP Server: A lightweight microservice exposing distinct primitives (Resources, Tools, and Prompts) over JSON-RPC 2.0 transports.

Core MCP Primitives

An MCP server exposes three main primitives to the AI host:

Primitive Nature Concept Example Use Case
Resources Read-Only Static or dynamic context payloads exposed as URI schemes (postgres://, file://). Reading a PDF contract, pulling a customer schema.
Tools Action-Oriented Callable functions with defined input parameters that execute actions or mutations. Executing a database query, triggering a webhook, creating a ticket.
Prompts Pre-packaged Standardized context templates provided by the server. "Debug build failure", "Generate quarterly report".

Building an Enterprise MCP Server in Python

Below is an example of an MCP server implemented using the official mcp Python SDK. It exposes a secure, read-only enterprise database lookup tool:

import asyncio
from mcp.server import Server, NotificationOptions
from mcp.server.models import InitializationOptions
import mcp.server.stdio
import mcp.types as types

# Initialize the MCP Server instance
app = Server("enterprise-db-server")

@app.list_tools()
async def handle_list_tools() -> list[types.Tool]:
    """Expose available database tools to the MCP client."""
    return [
        types.Tool(
            name="query-customer-record",
            description="Securely fetches customer details by Account ID.",
            inputSchema={
                "type": "object",
                "properties": {
                    "account_id": {
                        "type": "string", 
                        "description": "Unique enterprise account ID (e.g. ACC-1092)"
                    }
                },
                "required": ["account_id"],
            },
        )
    ]

@app.call_tool()
async def handle_call_tool(
    name: str, 
    arguments: dict | None
) -> list[types.TextContent | types.ImageContent | types.EmbeddedResource]:
    """Execute tool requests coming from the LLM via the MCP Client."""
    if name == "query-customer-record":
        account_id = arguments.get("account_id") if arguments else None
        
        # In production, query read-replicas behind access-controlled VPCs
        record = f"Account {account_id}: Tier=Enterprise, Status=Active, SLA=99.99%"
        
        return [
            types.TextContent(
                type="text",
                text=record
            )
        ]
    
    raise ValueError(f"Unknown tool request: {name}")

async def main():
    # Run the server over stdio for local sidecar process communication
    async with mcp.server.stdio.stdio_server() as (read_stream, write_stream):
        await app.run(
            read_stream,
            write_stream,
            InitializationOptions(
                server_name="enterprise-db-server",
                server_version="1.0.0",
                capabilities=app.get_capabilities(
                    notification_options=NotificationOptions(),
                    experimental_capabilities={},
                ),
            ),
        )

if __name__ == "__main__":
    asyncio.run(main())

Key Security & Governance Rules for Enterprise Deployments

Connecting LLMs directly to internal infrastructure carries inherent risk. When rolling out MCP servers across enterprise teams, follow these core security practices:

  1. Enforce Human-in-the-Loop Approval: Destructive or mutating tools (such as drop_table or send_payment) should require explicit confirmation at the MCP Client/Host level before execution.
  2. Principle of Least Privilege: Deploy MCP servers with minimal scoped credentials. Database servers should default to read-only connections with row-level security enabled.
  3. Avoid Context Window Pollution: When exposing hundreds of enterprise tools, avoid passing full schemas into every context window. Use code-execution patterns or dynamic discovery to keep context windows efficient.

Architectural Summary

The Model Context Protocol establishes a clean separation between AI client host applications and underlying enterprise datasets. By standardizing interfaces through MCP, organizations can build modular, secure tool ecosystems that work seamlessly across various LLM architectures.
