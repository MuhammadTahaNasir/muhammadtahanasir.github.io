Everything Was Fine... Until 10 Users Became 10,000

When we launched our AI document intelligence tool, the architecture was delightfully simple. A user uploaded a 50-page PDF, typed a prompt, and got an answer. In local development and early beta testing with 10 friends, the app felt instantaneous.

Then came launch day. A front-page feature on Product Hunt and a viral post on X brought 10,000 active users in under four hours.

Within 20 minutes, the application imploded:

  • HTTP 504 Gateway Timeouts: Next.js serverless functions hit 30-second execution limits waiting for long-running LLM completions.
  • Database Collapse: PostgreSQL threw FATAL: sorry, too many clients already as unpooled backend instances exhausted connection limits.
  • Event Loop Starvation: Synchronous PDF parsing functions locked up FastAPI's single-threaded asyncio loop, freezing API health checks for everyone.
  • Cascading Failures: Retrying failed user requests created a thundering herd that burned through our OpenAI API rate limits in minutes.

The site wasn't down because the stack was wrong, it was down because synchronous web architectures cannot handle long-running, non-deterministic AI inference workloads. Here is the story of how we re-architected the stack to handle 25,000+ concurrent users without breaking a sweat or burning through our cloud budget.

1. The MVP Architecture (And Why It Failed)

Our initial setup was the standard full-stack monorepo pattern recommended by hundreds of tutorials:

Why It Worked Initially

It was trivial to write. Next.js handled client state and routing. FastAPI accepted the request, made an ORM query to Postgres, called openai.chat.completions.create(), and returned JSON back to the browser.

Why It Exploded

  • Coupling Transport to Execution: The client HTTP connection stayed open for the entire duration of the AI pipeline (parse PDF $\rightarrow$ generate embeddings $\rightarrow$ vector search $\rightarrow$ LLM generation $\rightarrow$ DB write). If any step took longer than 30 seconds, cloud edge routers killed the socket.
  • Unpooled DB Connections: Every FastAPI request worker established a fresh connection to Postgres. Under load, 200 concurrent web requests spawned 200 database connections, instantly crashing a 2GB RAM database node.
  • Blocking the Async Loop: Calling synchronous libraries (like legacy pypdf or sync HTTP clients) inside FastAPI route handlers blocked Python's single-threaded event loop, preventing all other incoming requests from being processed.

2. Breaking Down the Production Architecture

To scale, we decoupled the synchronous user interface from asynchronous AI processing:

The Production Stack Components

  • Next.js 16 App Router: Renders UI components on the server (RSC) and consumes streaming AI output via Server-Sent Events (SSE).
  • FastAPI Backend: Acts strictly as an API gateway for validation, authentication, and job dispatching. It never waits for AI inference.
  • Redis + ARQ / Taskiq: Manages distributed task queues with automatic retries, backpressure, and job status tracking.
  • PostgreSQL + PgBouncer: Handles primary data storage, workspace multi-tenancy, and vector similarity search via pgvector.
  • AWS S3 / Cloudflare R2: Offloads all heavy file uploads (PDFs, images, transcripts) away from application memory.

3. Code Walkthrough: Asynchronous Streaming Pattern

Instead of keeping an HTTP connection hanging while the AI generates a response, the production endpoint pushes work to a task queue and streams results back over a dedicated channel.

Step A: FastAPI Non-Blocking Enqueue Endpoint

from fastapi import FastAPI, BackgroundTasks, Depends, HTTPException, status
from pydantic import BaseModel
import redis.asyncio as aioredis
import json
import uuid

app = FastAPI()
redis_client = aioredis.from_url("redis://localhost:6379/0")

class GenerationRequest(BaseModel):
    document_id: str
    prompt: str

@app.post("/api/v1/generate", status_code=status.HTTP_202_ACCEPTED)
async def submit_generation_job(
    payload: GenerationRequest,
    user_id: str = Depends(get_current_user_id)
):
    job_id = f"job:{uuid.uuid4()}"
    
    # 1. Store initial job state in Redis with 1-hour expiration
    job_data = {
        "status": "QUEUED",
        "user_id": user_id,
        "document_id": payload.document_id,
        "prompt": payload.prompt
    }
    await redis_client.setex(job_id, 3600, json.dumps(job_data))
    
    # 2. Push job ID to the worker queue
    await redis_client.rpush("queue:ai_jobs", job_id)
    
    # 3. Return 202 Accepted immediately (<20ms response time)
    return {"job_id": job_id, "stream_url": f"/api/v1/stream/{job_id}"}

Step B: Real-Time Server-Sent Events (SSE) Stream

from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import asyncio

@app.get("/api/v1/stream/{job_id}")
async def stream_job_output(job_id: str):
    """Streams real-time LLM tokens directly from Redis Pub/Sub to the client."""
    
    async def event_generator():
        pubsub = redis_client.pubsub()
        await pubsub.subscribe(f"channel:{job_id}")
        
        try:
            while True:
                message = await pubsub.get_message(ignore_subscribe_messages=True, timeout=1.0)
                if message:
                    data = message["data"].decode("utf-8")
                    if data == "[DONE]":
                        yield "data: [DONE]\n\n"
                        break
                    yield f"data: {data}\n\n"
                await asyncio.sleep(0.01) # Yield control back to event loop
        finally:
            await pubsub.unsubscribe(f"channel:{job_id}")

    return StreamingResponse(event_generator(), media_type="text/event-stream")

4. The Database Story: Postgres Under Pressure

PostgreSQL is an incredible primary database, but raw relational setups break under concurrent AI SaaS workloads without proper connection management and query indexing.

Solving Connection Exhaustion with PgBouncer

Running 50 background worker threads alongside 200 FastAPI instances will crash Postgres if each process opens a direct connection. We deployed PgBouncer in transaction pooling mode in front of Postgres:

  • Direct Postgres Connections: Capped at 50 persistent connections allocated to PgBouncer.
  • Client App Connections: PgBouncer accepts up to 5,000 incoming client connections, routing active SQL transactions to the 50 underlying server slots.
[databases]
app_production = host=127.0.0.1 port=5432 dbname=app_production

[pgbouncer]
pool_mode = transaction
max_client_conn = 5000
default_pool_size = 50
reserve_pool_size = 10

Indexing Vector & Relational Data Correctly

In 2026, using pgvector inside Postgres simplifies infrastructure by keeping relational metadata and vector embeddings in a single ACID-compliant database. However, vector searches will degrade without proper index configuration:

-- 1. Create compound B-Tree index for tenant isolation (CRITICAL for SaaS)
CREATE INDEX CONCURRENTLY idx_document_chunks_tenant_doc 
ON document_chunks (tenant_id, document_id);

-- 2. Create HNSW vector index for ultra-fast cosine distance search
CREATE INDEX CONCURRENTLY idx_document_chunks_embedding_hnsw 
ON document_chunks 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

By ensuring queries always filter by tenant_id first before applying vector similarity calculations, search latency dropped from 850ms to 12ms.

6. The Engineering Reality: What Wakes You Up at 3 AM

Architectural diagrams always look clean. Production is messy. These are the three subtle bugs that tripped us up during real-world scaling:

A. The Silent Event Loop Blocker

Python's async/await syntax is cooperative. If a third-party package performs a synchronous operation (like standard requests.get() or a CPU-heavy tokenizer), it blocks the entire asyncio thread.

The Fix: Wrap all synchronous or CPU-bound operations in asyncio.to_thread() or offload them to dedicated worker processes:

# BAD: Blocks the event loop for all users during heavy parsing
# text = sync_pdf_parser(file_bytes)

# GOOD: Offloads CPU-bound parsing to worker thread pool
text = await asyncio.to_thread(sync_pdf_parser, file_bytes)

B. Concurrent Token Balance Race Conditions

When multiple requests hit the backend simultaneously to update a workspace's remaining AI credit balance, standard UPDATE queries cause race conditions or deadlocks.

The Fix: Use atomic database operations or row-level locking:

-- Prevents race conditions by modifying value atomically in Postgres
UPDATE workspaces 
SET credit_balance = credit_balance - 1 
WHERE id = 'ws_123' AND credit_balance >= 1;

C. N+1 Query Explosions in ORMs

When rendering workspace analytics, SQLAlchemy or Prisma often defaults to issuing hundreds of individual queries in a loop to fetch nested user relationships.

The Fix: Use EXPLAIN ANALYZE on every route during testing and enforce explicit eager loading (selectinload() in SQLAlchemy or include in Prisma).

7. Infrastructure & Deployment Setup

To keep operations maintainable, we containerized services with Docker and deployed behind Nginx for SSL termination, request buffering, and CORS handling.

Dockerfile

# Multi-stage Dockerfile for FastAPI Backend
FROM python:3.11-slim AS builder

WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends gcc python3-dev

COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /install /usr/local
COPY ./app /app/app

# Run Uvicorn with gunicorn process manager
CMD ["gunicorn", "app.main:app", "-w", "4", "-k", "uvicorn.workers.UvicornWorker", "-b", "0.0.0.0:8000"]

Nginx SSE Configuration Rule

When routing Server-Sent Events through Nginx, you must disable proxy buffering, otherwise Nginx will hold back streamed AI tokens until the buffer fills up:

location /api/v1/stream/ {
    proxy_pass http://fastapi_backend;
    proxy_set_header Connection '';
    proxy_http_version 1.1;
    proxy_buffering off; # CRITICAL: Allows instant streaming of AI tokens
    proxy_cache off;
    chunked_transfer_encoding on;
}

Summary

Scaling an AI SaaS application isn't about choosing the "fastest" framework or chasing complex infrastructure trends. It comes down to a few core engineering principles:

  • Decouple web servers from execution loops: Use queues for long-running AI jobs and stream responses asynchronously via SSE or WebSockets.
  • Protect your database: Use connection poolers (PgBouncer) and compound indexes to keep database queries under 15ms.
  • Keep the event loop free: Never run synchronous I/O or heavy CPU operations on your primary async thread.
