Modern AI Still Has to Speak the Language of Legacy Phone Systems

When people imagine Voice AI, they picture cutting-edge language models holding natural conversations in real time. What they don't see is the technology sitting between the customer and the AI.

Most phone calls still travel across infrastructure that was designed decades ago. An enterprise customer calls your support number: their voice isn't streamed as pristine 48kHz stereo audio, it arrives as 8kHz mono G.711 μ-law audio, a codec introduced long before generative AI existed.

If you want that customer to speak naturally with GPT-powered assistants, Claude, Gemini, or any modern speech model, you first have to bridge two completely different worlds: one is built around legacy telephony standards, while the other expects modern streaming APIs, low-latency audio pipelines, and asynchronous inference.

Building that bridge turned out to be one of the most interesting engineering challenges we encountered.

This article walks through how we connected Twilio Media Streams to a real-time AI backend using Python, handled μ-law audio decoding, supported full-duplex conversations, and built production-ready enterprise voice agents.

1. Bridging Legacy Telephony and Generative AI

A typical AI chatbot only exchanges text. Voice agents are significantly more complicated. Instead of processing one prompt every few seconds, they must continuously process incoming audio while simultaneously generating spoken responses.

The pipeline looks something like this:

  • Receive audio from the phone call.
  • Decode legacy telephony audio.
  • Convert audio into text using Speech-to-Text.
  • Send the transcript to an LLM.
  • Generate a response.
  • Convert text back into speech.
  • Stream audio back to the caller.

Every stage adds latency. Even small delays become noticeable during natural conversation. Keeping end-to-end latency below a few hundred milliseconds becomes just as important as choosing the language model itself.

2. Understanding Twilio Media Streams

Twilio Media Streams provide a real-time WebSocket connection directly from an active phone call. Instead of receiving a completed recording after the call ends, your application receives audio continuously while the caller is speaking.

Each message is delivered as JSON. The important event types include:

  • start – A new call begins.
  • media – Contains audio payloads.
  • mark – Optional synchronization markers.
  • stop – Indicates the call has ended.

Audio is delivered as base64-encoded G.711 μ-law samples in approximately 20-millisecond chunks. That small chunk size allows applications to process speech almost immediately instead of waiting for long recordings to finish.

Streaming architecture is what makes conversational AI feel natural instead of delayed.

3. Why μ-law Audio Needs Conversion

Most modern speech recognition systems expect linear PCM audio sampled at 16kHz or higher. Traditional telephone networks don't. Instead they use G.711 μ-law, 8kHz sample rate, mono channel, and 8-bit compressed audio.

The result is excellent compatibility with existing telephone infrastructure but poor compatibility with AI speech models.

Before sending audio into a Speech-to-Text engine, it must be Base64 decoded, μ-law decoded, converted into linear PCM, and resampled from 8kHz to 16kHz.

Only then is the audio suitable for transcription. Although these transformations happen in milliseconds, they're essential for accurate speech recognition.

4. Building the Streaming FastAPI Server

FastAPI provides an excellent foundation for handling Twilio's persistent WebSocket connections. Each incoming connection represents a live phone call. As audio frames arrive, the server continuously processes them without blocking other active conversations.

Streaming Transcoder Python Blueprint

import base64
import audioop
import json
from fastapi import FastAPI, WebSocket

app = FastAPI()

@app.websocket("/ws/twilio")
async def twilio_audio_ws(websocket: WebSocket):
    await websocket.accept()
    stream_sid = None

    async for message in websocket.iter_text():
        data = json.loads(message)
        event = data.get("event")

        if event == "start":
            stream_sid = data["start"]["streamSid"]
            print(f"Call started with Stream SID: {stream_sid}")

        elif event == "media":
            payload_b64 = data["media"]["payload"]
            mulaw_bytes = base64.b64decode(payload_b64)

            # Transcode 8kHz μ-law to 16kHz 16-bit Linear PCM
            pcm_16k, _ = audioop.ratecv(
                audioop.ulaw2lin(mulaw_bytes, 2),
                2,
                1,
                8000,
                16000,
                None,
            )

            # Forward PCM audio to your streaming STT engine

        elif event == "stop":
            print("Call ended by user.")

Rather than processing complete recordings, the server continuously transforms tiny audio frames into PCM that can immediately be consumed by a streaming Speech-to-Text engine. This streaming approach dramatically reduces conversational latency.

5. Connecting STT, LLM, and TTS

Once audio has been converted into PCM, the rest of the pipeline follows a familiar pattern.

Speech-to-Text generates partial transcripts as the user speaks. Instead of waiting for complete sentences, modern streaming recognizers continuously emit interim results. These transcripts are forwarded to the language model, which begins generating a response as soon as sufficient context becomes available.

Finally, Text-to-Speech converts the generated text into audio chunks that are streamed back through Twilio.

Rather than thinking of these as separate services, it's helpful to imagine them as one continuous pipeline where every component operates simultaneously. The faster each stage begins processing, the more natural the conversation feels.

6. Full-Duplex Conversations

One of the defining characteristics of natural conversations is that people don't politely wait for each other to finish every sentence. They interrupt, correct themselves, and change topics halfway through.

Voice AI should behave the same way. This capability is known as full-duplex communication.

Instead of alternating between speaking and listening, the system can receive incoming speech while simultaneously generating outbound audio. Achieving this requires careful orchestration: speech recognition, language model inference, audio synthesis, and media streaming all operate concurrently without blocking one another.

7. Handling Barge-In

One of the first features enterprise customers request is interruption support.

As soon as incoming speech is detected, outbound speech playback stops, remaining audio buffers are discarded, the active LLM response is cancelled, and the new transcript becomes the current conversation context.

From the caller's perspective, the assistant behaves much more like a human conversation partner. Supporting barge-in dramatically improves perceived intelligence even though the underlying model hasn't changed.

8. Scaling Enterprise Voice Agents

Voice systems introduce challenges that text chat applications rarely encounter. A single active conversation consumes persistent WebSocket connections, streaming STT/TTS sessions, continuous LLM inference, audio transcoding, and session state.

Production deployments typically separate responsibilities: FastAPI gateways manage WebSockets, background workers handle transcription and synthesis, Redis manages session state, message queues distribute inference workloads, object storage archives recordings, and PostgreSQL stores metadata and transcripts.

9. Security, Compliance, and Observability

Enterprise voice applications process highly sensitive information in financial, healthcare, insurance, and customer support centers. Production systems require end-to-end TLS encryption, consent handling for recorded calls, PCI/HIPAA compliance, automatic transcript redaction, role-based access control, and immutable audit logs.

Observability metrics such as active calls, average response latency, speech recognition accuracy, audio packet loss, LLM response time, barge-in frequency, and WebSocket disconnect rates help identify issues long before callers report poor experiences.

10. Lessons from Production

Building Voice AI isn't primarily a machine learning problem, it's a systems engineering problem. The speech model is only one piece of a much larger architecture.

Reliable voice agents require low-latency streaming, efficient audio transcoding, asynchronous processing, robust retry logic, careful session management, and monitoring across every service.

Summary

Connecting traditional telephony infrastructure with modern generative AI requires much more than plugging an LLM into a phone system. The biggest lessons we learned were straightforward:

  • Legacy telephony standards require careful audio transcoding: Decode 8kHz G.711 μ-law into 16kHz linear PCM before feeding speech models.
  • Twilio Media Streams enable real-time conversations: Stream small 20ms audio frames over WebSockets rather than processing static files.
  • Low-latency voice depends on asynchronous pipelines: STT, LLM inference, and TTS synthesis must run concurrently.
  • Full-duplex & barge-in support are mandatory: Flushed audio buffers and immediate task cancellation make AI conversations feel natural.
