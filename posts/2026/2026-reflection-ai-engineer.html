Four Years Later: What Building AI Products Actually Looks Like

June 1, 2026 • 4 min • Muhammad Taha Nasir

Looking Back at the Spaghetti Code

I was cleaning out some old GitHub repositories last night and stumbled across the very first natural language processing project I built back in 2023. Looking at the code was a humbling experience. It was a tangled, procedural web of massive functions, hardcoded absolute file paths, and zero error handling. If an API failed, the entire script crashed silently.

It forced me to pause and reflect. The landscape of software engineering has shifted dramatically over the past four years, and my own mindset has had to mature rapidly just to keep pace with the industry. The jump from a student stringing together tutorial code to an engineer architecting reliable systems is immense.

The Shift: Systems over Algorithms

When you first learn computer science, the academic focus is entirely on algorithms. You learn syntax, data structures, and the theoretical math behind machine learning models. I spent months in my early days obsessing over hyperparameter tuning, trying to get a neural network's training loss down by a fraction of a percent.

The harsh reality of the tech industry is that users do not care about your training loss. They do not care if you used a sophisticated transformer architecture or a simple regex script. They care about two things: Does the product solve their problem, and is it fast?

Building real AI products means shifting your focus away from the model and towards the system. You have to deal with asynchronous database pools, manage cloud deployment pipelines via GitHub Actions, orchestrate Docker containers, and set up telemetry to monitor data drift. The machine learning model is no longer the entire project; it is just a single, fragile gear inside a massive engine.

The Marks of Engineering Maturity

I realized I was maturing as an engineer when I stopped looking for the "newest" framework and started looking for the "most stable" framework. In 2023, I wanted to rewrite everything every time a new library dropped on HackerNews. Today, I value boring, predictable technology like PostgreSQL and stable FastAPI instances.

Maturity in engineering is understanding trade-offs. It is knowing when to use a massive cloud LLM and when to use a simple, quantized local model. It is understanding that adding complexity to a system increases the surface area for catastrophic bugs.

Embracing the Failures

Every major architectural lesson I have learned over these four years came from a system breaking in production. I learned about GPU memory quantization only because an AWS instance ran out of VRAM and crashed during a demo. I learned about semantic caching because my unoptimized API was timing out under heavy concurrent load. I learned about Docker because of the dreaded "it works on my machine" dependency nightmare.

Failure is the most effective technical instructor. You cannot read a textbook to learn how a system behaves under pressure. You have to build it, deploy it, watch it break, parse through the messy error logs, and rebuild it stronger.

Moving Forward

The biggest piece of advice I can offer to anyone entering the software or AI space right now is to escape tutorial purgatory immediately. Stop copying code from videos. Build your own systems, push them to the public internet, and let the real world break them. Engineering is nothing more than a continuous, infinite loop of problem-solving.

To everyone who has read these posts, sent me emails, or collaborated on GitHub over the years—thank you. The grind continues. Onwards and upwards.
