Fast AI Isn't About Faster Models. It's About Smarter Systems.

When people think about reducing AI latency, the first instinct is usually to buy bigger GPUs. Upgrade from an L4 to an A100. Add another inference server. Switch to a newer language model.

Those upgrades certainly help, but they rarely solve the biggest bottlenecks.

When we launched our AI-powered knowledge assistant, we assumed inference speed would be limited by the model itself. We were wrong.

Even though our GPUs were barely reaching 45% utilization, users were waiting nearly two seconds before seeing the first generated token. Requests piled up. Costs increased. Throughput remained disappointing.

After profiling the entire inference pipeline, we realized the model wasn't the problem: the surrounding infrastructure was.

Duplicate prompts were being recomputed thousands of times every day. GPU kernels were processing tiny batches instead of full workloads. Prompt preprocessing consumed more time than inference itself. Every request was treated as completely unique, even when users were asking nearly identical questions.

Instead of replacing the model, we rebuilt the serving architecture. The result was dramatic: average latency dropped by more than 50%, throughput nearly tripled, and infrastructure costs fell despite handling significantly more traffic.

This is how we optimized production AI inference using semantic caching, intelligent request batching, and vLLM.

1. Why AI Feels Slow

Most production inference pipelines spend surprisingly little time actually generating text. Instead, latency accumulates across multiple stages:

  • Authentication & Request validation
  • Prompt construction & Embedding generation
  • Vector search & Tokenization
  • GPU scheduling & Model inference
  • Response formatting & Network transmission

Each stage adds milliseconds. Individually they seem insignificant. Together they determine how responsive the application feels. Reducing latency isn't about optimizing a single component: it's about removing unnecessary work throughout the entire pipeline.

2. The Cost of Repeated Questions

One of the first patterns we noticed was surprisingly simple: users asked the same questions repeatedly.

Examples included: "Summarize this contract.", "What are the payment terms?", "List key risks.", "Explain this invoice."

Although the wording differed slightly, the intent was nearly identical. Our infrastructure treated every request as completely new. The same documents were embedded again, the same context was retrieved, the same prompts were sent to the language model, and the GPU generated nearly identical responses over and over again. We were wasting expensive compute on work we had already completed.

3. Semantic Caching Instead of Exact Matching

Traditional caches only work when requests are identical. AI applications rarely receive identical prompts. Instead, they receive semantically similar ones.

Python Semantic Cache Blueprint

import numpy as np
from qdrant_client import QdrantClient
from sentence_transformers import SentenceTransformer

class SemanticCache:
    def __init__(self, threshold: float = 0.92):
        self.encoder = SentenceTransformer("all-MiniLM-L6-v2")
        self.client = QdrantClient("http://localhost:6333")
        self.threshold = threshold

    async def get_response(self, prompt: str) -> str | None:
        vector = self.encoder.encode(prompt).tolist()
        results = self.client.search(
            collection_name="semantic_cache",
            query_vector=vector,
            limit=1,
            score_threshold=self.threshold
        )
        if results:
            return results[0].payload["response"]
        return None

4. Smarter Request Batching

GPUs perform best when processing many requests simultaneously. Unfortunately, most inference servers execute requests one at a time as they arrive. Small batches waste GPU resources, while large batches increase waiting time. Finding the right balance is critical.

Instead of immediately executing every incoming request, we introduced dynamic batching. Requests arriving within a very small scheduling window were grouped together before inference. Rather than serving one request at a time, the GPU processed dozens simultaneously.

The improvement wasn't linear: GPU utilization increased significantly while average latency actually decreased because hardware resources were finally being used efficiently.

5. Why We Switched to vLLM

Initially we served models using standard Hugging Face inference pipelines. They worked well for development but became increasingly inefficient under production traffic: memory fragmentation increased over time, prompt processing duplicated work, and GPU utilization remained inconsistent.

Async vLLM Integration Blueprint

from vllm import AsyncLLMEngine, AsyncEngineArgs, SamplingParams

engine_args = AsyncEngineArgs(
    model="meta-llama/Meta-Llama-3-70B-Instruct",
    tensor_parallel_size=2,
    gpu_memory_utilization=0.90,
    max_num_seqs=256,
    enable_prefix_caching=True  # Automatic KV cache reuse
)
engine = AsyncLLMEngine.from_engine_args(engine_args)

async def generate_stream(prompt: str, request_id: str):
    sampling_params = SamplingParams(temperature=0.7, max_tokens=512)
    results_generator = engine.generate(prompt, sampling_params, request_id)
    async for request_output in results_generator:
        yield request_output.outputs[0].text

6. Optimizing the KV Cache

One overlooked source of latency is repeatedly recomputing attention states for long prompts. Every generated token depends on previously processed tokens. Without an efficient KV cache, the model performs unnecessary calculations repeatedly.

Modern inference engines store these intermediate attention values in GPU memory. When prompts share common prefixes or conversations continue across multiple turns, previously computed states can be reused instead of recalculated.

Reducing redundant computation became especially valuable for document chat applications where users often asked multiple follow-up questions about the same context.

7. Streaming Responses Earlier

Users care less about total completion time than they do about how quickly something appears on the screen. Waiting two seconds before the first generated token feels slow. Waiting 200 milliseconds before streaming begins feels almost instant, even if the final response still takes several seconds.

Instead of waiting for complete generations, we streamed tokens as soon as they became available. Time-to-first-token became one of our primary optimization metrics. Perceived performance improved dramatically even though total inference time changed only slightly.

8. Eliminating Bottlenecks Outside the Model

Profiling revealed that many slow requests had nothing to do with inference. Some common bottlenecks included:

  • Slow database queries
  • Excessive prompt formatting
  • Repeated embedding generation
  • Large document serialization
  • Inefficient network calls & Blocking API endpoints

Improving these components often produced larger latency reductions than optimizing the language model itself. One optimized SQL query sometimes saved more time than upgrading GPU hardware.

9. Measuring What Actually Matters

Average latency alone doesn't tell the whole story. We focused on several key production metrics: Time to First Token (TTFT), Tokens Generated per Second, GPU Utilization, Queue Wait Time, Batch Size, Cache Hit Rate, Memory Utilization, and Concurrent Requests.

Tracking these metrics revealed optimization opportunities that would have remained invisible if we only monitored average response times.

10. Lessons from Production

The biggest surprise wasn't that GPUs were expensive: it was how much performance we were leaving unused. The language model wasn't inherently slow, our serving architecture was inefficient.

Semantic caching eliminated redundant inference, dynamic batching maximized GPU throughput, vLLM reduced memory overhead, and streaming improved perceived responsiveness. Together, these changes transformed the user experience without requiring larger models or dramatically increasing infrastructure costs.

Summary

Fast AI systems aren't built by deploying larger models. They're built by eliminating unnecessary computation. The biggest lessons we learned were straightforward:

  • Measure the entire inference pipeline: Optimize prompt preprocessing and database calls alongside model execution.
  • Use semantic caching: Eliminate redundant inference by matching prompt vectors against previous cached queries.
  • Batch requests intelligently: Maximize GPU utilization using dynamic continuous batching without increasing latency.
  • Adopt optimized engines like vLLM: Utilize PagedAttention to eliminate memory fragmentation and unlock 3x higher concurrency.
